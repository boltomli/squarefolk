# Core Spec — 语言无关核心规格

> **状态：骨架（M0 进行中）** · 与 design.md 版本对齐（v0.9）
> 本文件是项目里**唯一可编码的规格**：任何语言的实现以「本文件 + 黄金向量」为准。
> 与 `design.md` 冲突时**先报告再改稿**，不要在实现里自行取舍。
> 红线与交付标准见仓库根目录 [AGENTS.md](../AGENTS.md)。

## 0. 全局约定

| 项 | 约定 | 状态 |
| --- | --- | --- |
| 数值定点 | 属性 ×10 存储（支持 0.5 步进）；中间运算 64 位整数 | ✅ design §5.2 |
| 舍入 | 只在**最终一步** half-up，不使用语言自带 round() | ✅ design §5.2 |
| id | 字符串 `domain.name`（`unit.warrior`）；持久化禁止枚举整数 | ✅ design §6 |
| 距离 / 邻接 | 切比雪夫距离 `max(|dx|,|dy|)`；**8 向邻接**（含对角） | ✅ design §2.2 / D1 |
| 随机 | 战斗与结算路径**零随机**；PRNG 仅用于世界生成 | ✅ design §5.2 |
| PRNG 算法 | 🔶 待定（splitmix64 / PCG32 二选一，选定后逐位写死序列） | 🔶 |
| 序列化 / stateHash | 规范 JSON（键字典序、无空白、无浮点）→ 64 位哈希；算法 🔶 待定（FNV-1a 64 / xxHash64） | 🔶 |
| 遍历顺序 | 一切集合结算前按 id / 坐标显式排序 | ✅ design §5.2 |
| 版本 | `rulesVersion`（规则语义）与 `schemaVersion`（数据结构）双轨 | ✅ design §6 |

## 1. 状态模型 `State`（草案 —— 待展开）

| 字段 | 类型（语义） | 说明 |
| --- | --- | --- |
| `rulesVersion` / `contentHash` | string | 回放与对账必备 |
| `seed` / `world` | 整数种子 / 地图数据 | 种子只决定世界，不参与战斗结算 |
| `tiles[]` | 二维 | 地形、资源、城址、归属 |
| `units[]` | 列表 | id、归属、类型、坐标、HP、`acted`（姿态来源）、晋升计数 |
| `players[]` | 列表 | 星星、科技集合、阵营、视野数据 |
| `cities[]` | 列表 | 等级、人口、城墙耐久、围城状态 |
| `turn` / `currentPlayer` | 整数 | |
| `actionLog[]` | 列表 | `{seq, playerId, actionType, payload}`，唯一事实源 |

> 展开时必须给出：每个字段的精确类型、取值范围、不变量（如 `0 ≤ hp ≤ maxHp`）、序列化顺序。

## 2. 动作类型 `Action`（草案）

| action | payload | 校验要点 |
| --- | --- | --- |
| `move` | unitId, to | 合法路径、移动力、ZOC、地形通行 |
| `attack` | unitId, targetId | 距离 ≤ 射程、目标可见、姿态判定 |
| `harvest` | unitId | 资源存在、科技解锁 |
| `build` | cityId, kind | 星星足够、地块合法、边际成本 |
| `research` | techId | 星星足够、前置科技 |
| `upgradeCity` | cityId, choice | 人口足够、三选一 |
| `heal` | unitId | 本回合未移动/攻击 |
| `endTurn` | — | 提交后不可撤销 |

> 展开时给出每个动作的 `legalActions` 判定条件（谓词列表），UI 高亮、bot、联机校验**共用**这一份。

## 5. 边界情况清单（持续补充，每条必须有对应向量）

- [ ] 0 血单位参与结算、致死与垂死反击取整（`基数 × 25%` 后可能为 0 或 1）
- [ ] `DEF_eff` 触顶（> 5 时截断）与 0 防单位
- [ ] 同归于尽（双方同时致死）
- [ ] 近战击杀补位受阻（目标格不可进入）
- [ ] ZOC 与道路 0.5 费叠加、剩 0.5 移动力时向上取整
- [ ] 姿态切换时机（本回合行动后 vs 下回合生效）、新建单位视为防御姿态
- [ ] 围城进度、城墙耐久归零与占领同回合
- [ ] 城市升级人口溢出、遗迹一次性奖励的取整
- [ ] 视野裁剪：`viewFor` 对未探索/已探索无视野/可见三态的输出

## 6. 黄金测试向量格式

路径：`testdata/golden/<域>/<用例名>.json`

```json
{
  "id": "combat/non-defensive-first-strike-01",
  "rulesVersion": "0.1.0",
  "source": "design.md §3.7 行1",
  "given": {
    "state": { "…最小可复现状态…": "…" },
    "action": { "type": "attack", "unitId": "u1", "targetId": "u2" }
  },
  "expect": {
    "state": { "…断言关心的字段子集…": "…" },
    "hash": "…可选，完整状态时给…"
  },
  "notes": "步兵 vs 非防御姿态步兵：主动 5、反击 5，3 刀分胜负"
}
```

**向量纪律**

1. 数值**由规格手算或推导**得出（design §3.7 是第一批的来源），**禁止由实现反向生成**（防循环论证）
2. 每条向量必须能在任意语言实现上独立断言，不依赖实现细节
3. `expect` 只断言规格关心的字段；给 `hash` 的必须是规范化序列化后的完整状态
4. 新增规则 → 必须同时新增向量；改规格 → 向量与修订记录同步更新

**首批目标（M0）**：design §3.7 的 8 组战斗标定 → `combat/`；姿态切换、ZOC、垂死反击取整 → `combat/boundary-*`；固定种子地图指纹 → `world/gen-*`。

## 7. 版本与兼容

- `rulesVersion` 变更 → 旧回放必须用对应版本实现才能复现（回放头部记录）
- `schemaVersion` 变更 → 数据需迁移函数
- 语义化：破坏规则语义 = minor+1（1.0 前）；纯内容数值调整不改 `rulesVersion`，只改 `contentHash`
